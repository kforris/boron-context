# Boron Context v0.4.0 — Human-reviewable Boron Content

Version 0.4.0 turns the existing read-only meter into a practical local review surface for all
three Boron layers, while keeping Boron itself deterministic and model-free.

## What changed

- The macOS menu panel no longer wraps its content in a fixed `690 pt` scroll view. It now sizes to
  its content; `Command-plus` and `Command-minus` scale text and window together while a dynamic
  70%-of-screen cap keeps every section visible without an internal scrollbar.
- Explicit high-contrast foreground colors fix the unreadable dark-on-dark audit text.
- The top `Content` action opens an authenticated Boron Content Inspector.
- Ontology entities and current relations are rendered as a clickable PostgreSQL knowledge graph.
- The maintained Codebase Memory 3D graph remains the code-structure owner and is reused rather
  than reimplemented.
- OpenWiki renders local Markdown as a documentation site with navigation and a correction pane.
- Every correction is stored as revisioned `pending` evidence. It does not directly modify source
  objects, relations, graph indexes, or Markdown.

## Menu panel — complete content, keyboard zoom, no internal scrollbar

![Full-height Boron Content menu panel](https://raw.githubusercontent.com/kforris/boron-context/v0.4.0/docs/assets/screenshots/v0.4.0/boron-menu-panel.png)

The live window reached `482 × 714 pt` at `118%` zoom on a desktop with `1020 pt` of visible
vertical space. The cap therefore lands exactly at 70%. `Command-plus` and `Command-minus` scale
the text and window together, `Command-0` resets to 110%, and the chosen value persists across app
restarts. All meter sections, the latest Retrieval Plan, runtime tiles, repository action, zoom
controls, and measurement disclaimer stay visible at once. The implementation contains no
`ScrollView` and no fixed vertical frame.

## Ontology — entity and relationship review

![PostgreSQL ontology knowledge graph](https://raw.githubusercontent.com/kforris/boron-context/v0.4.0/docs/assets/screenshots/v0.4.0/ontology-graph.png)

PostgreSQL `objects` and `current_relations` produce the graph. Confirmed and candidate states stay
visible. Clicking a node or relation fills the side form; saving creates a pending correction and
does not overwrite the source row.

## Codebase Memory — maintained 3D graph

![Codebase Memory graph](https://raw.githubusercontent.com/kforris/boron-context/v0.4.0/docs/assets/screenshots/v0.4.0/codebase-graph.png)

The screenshot is the maintained Codebase Memory viewer, not a duplicated Boron graph. The tested
Boron Context index contained 560 nodes and 1,129 edges. Boron owns the loopback lifecycle and the
adjacent correction targeting, while Codebase Memory owns symbol and dependency truth.

## OpenWiki — documentation-style project knowledge

![OpenWiki reader](https://raw.githubusercontent.com/kforris/boron-context/v0.4.0/docs/assets/screenshots/v0.4.0/openwiki.png)

The light three-column reader uses a public example under `docs/examples/openwiki`. Runtime home
paths are displayed with `~` so screenshots and daily review do not expose a local username. Page
title, path, and rewrite instructions can be proposed from the correction pane.

## Agent-mediated correction loop

1. A person selects an ontology entity or relation, Codebase Memory symbol, or Wiki page.
2. Boron stores the fields and instruction in PostgreSQL as a revisioned pending correction.
3. The next Boron-enabled agent receives that correction as high-authority human review evidence.
4. The agent checks the current ontology, repository, and Wiki before repairing or rejecting the
   semantic relationship.
5. The agent explicitly resolves or dismisses the correction with an evidence-backed summary.

Boron Content owns zero LLM calls throughout this flow.

## Security boundaries

- The Inspector is loopback-only by default.
- A one-time launch ticket stays in the URL fragment and is exchanged for an `HttpOnly`,
  `SameSite=Strict` session cookie.
- Browser writes require a CSRF token.
- Unknown project scopes fail closed instead of returning all projects.
- The Wiki reader rejects symlinks and enforces per-page, total-size, depth, and page-count limits.
