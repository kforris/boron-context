# Boron Context v0.9.0 — Trusted continuity

Version 0.9.0 moves the product milestone toward a new task accurately continuing a real project:
keep current facts correct, retrieve decisions relevant to the question, and connect selected
context to an explicit report of what the task did with it. The implementation adds reusable
mechanisms and regression coverage. It does not claim that a live repair or the planned real-task
acceptance series has already completed.

## Fact changes with preserved history

The GitHub PR reconciliation CLI reads an exact registered project, repository and PR, produces a
reviewable plan, revalidates both sources before apply, and records the state replacement as one
guarded activity. Terminal PR states retract obsolete review-waiting state; existing historical
relations remain inspectable. Unknown sources or identities fail closed. It uses no model calls,
GitHub writes or background polling.

Capsules explicitly distinguish historical activity observations from current typed state and
its asserting source evidence. Old text remains available for historical explanation with an
as-of label, rather than appearing as an unqualified statement of the current state.

`record_activity` accepts optional relation preconditions. Transactions acquire subject locks and
compare the complete active relation-ID set before changing it. Identical idempotent retries are
recognized before retraction governance; a different payload or session cannot reuse the key.
The helper requires the daemon's advertised guard capability and verifies both ontology and GitHub
after a write. Unverified or unknown write outcomes produce a retained receipt instead of success.

See [Trusted continuity](../trusted-continuity.md) for the plan/apply workflow, timestamps, limits
and retry semantics.

## Relevant retrieval and observable use

Deterministic intent routing and relevance ranking handle English and Chinese continuation,
vision and decision questions. Requested source anchors are retained without allowing incidental
mentions of an unrelated source to select it. Regression cases cover relevant project decisions
being crowded out by repeated operational audit activity.

`record_context_use` links a task's `applied`, `rejected` or `stale` report to selected evidence from
a capsule in the same project and to URI-backed outcome evidence. `get_context_use_health` exposes
counts and the explicit basis `client_report_with_validated_selection`. This proves the reported
link passed selection and scope validation; adoption and outcome remain client reports. It is not
an independent task-quality score, a causal benefit claim or a substitute for a reviewer inspecting
the task output.

## Accounting and lifecycle correctness

- The context meter adds signed `sourceWindow.netSavingsTokens`, preserving negative expansion
  among measured source windows. Legacy nonnegative savings remains for compatibility. Neither
  figure covers unmeasured sources or downstream agent billing.
- The menu displays signed shrinkage or expansion, with unknown and legacy-estimate states.
  Its validated loopback URL and token-path overrides also isolate upgrade-rehearsal menus from
  the production daemon, including the disposable prior-version rollback client.
- Session completion records its terminal activity and closes the session in one transaction.
  Failed relation validation cannot leave a falsely completed session.
- Completed-session activity writes return a lifecycle conflict, and internal gateway errors use
  bounded, credential-redacted diagnostics with trace correlation.

## Acceptance and remaining work

Verification includes deterministic retrieval regressions, PR state reconciliation and API-boundary
tests, guarded writeback/idempotency tests, and PostgreSQL integration coverage. Test receipts and
exact release-commit CI results remain the source of truth for a particular build.

Production deployment, source/runtime parity, a live stale-fact repair and fresh-task readback each
require their own evidence. The planned real-task evaluation across three project workflows must
record critical omissions, stale-fact use, repeat queries, human corrections and inspected outputs.
Passing synthetic tests or receiving context-use reports does not mark that evaluation complete.

This version keeps the source-installed macOS + Codex deployment boundary. Linux packaging and
broader distribution remain future work; they are not required to start validating useful continuity
in the supported workflow.
