# Boron Context v0.7.6 — Source-coverage eligibility

Version 0.7.6 corrects the source-window coverage denominator for macOS + Codex product health.
It remains a productization milestone and does not authorize public release, Marketplace
submission, paid activity, or marketing.

## Acceptance contract

- HTTP, MCP, context-quality health, the authenticated Inspector, and the native menu bar report a
  measured numerator, eligible denominator, ratio, ineligible exclusions, unobservable evidence,
  and reason counts for both 7-day and 30-day windows;
- selected ontology entities and relations are labelled `ontology_derived` and excluded because
  they have no original source window to measure;
- live evidence without a source size remains eligible but unmeasured, while legacy activity and
  snapshot evidence with unknown size is unobservable rather than silently counted as a miss;
- old mixed fields remain available for client compatibility, and migration 012 adds labels without
  rewriting historical evidence or inventing source sizes;
- live Codebase Memory files, local Markdown, and upstream HTTP evidence record an explicit
  measured/unavailable source-size status and estimation basis; and
- unit and temporary-PostgreSQL fixtures cover measured live/snapshot/recorded evidence,
  unavailable live sources, ontology-derived data, legacy unknown-size records, and samples without
  evidence-level audit rows.

## Product-health interpretation

Use `sourceWindow.eligibility.ratio` for the release-candidate gate. The historical
`sourceWindow.coverageRatio` divides measured evidence by every selected item and is retained only
for compatibility. Savings totals still include only evidence with a real `sourceTokenEstimate`.
Neither an exclusion nor an unobservable item is treated as measured.

## Remaining release-candidate gates

After deployment and a live 7-day/30-day audit, the next bounded milestone is the 0.8 isolated
new-install/upgrade/uninstall/rollback rehearsal and formal release checklist. Public release still
requires a separate human go/no-go decision.
